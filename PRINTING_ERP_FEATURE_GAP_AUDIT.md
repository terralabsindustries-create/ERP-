# Printing ERP competitive feature-gap audit

**Audit date:** 27 November 2026 (India)  
**Scope:** repository at `Terra Erp`; read-only application audit. No production credentials, production data, live provider accounts, or customer/browser acceptance environment were supplied. No application source was changed. This document is the audit deliverable.

## Executive assessment and evidence standard

The application is a React/Vite frontend, Express API, and Mongoose/MongoDB data model, with an Electron desktop wrapper. `client/src/App.tsx` and `client/src/components/layout/Layout.tsx` define navigation; `backend/src/app.js` mounts APIs with `moduleGuard`; `backend/src/models/` contains the operational schema. The sole formal migration is `backend/migrations/add-datascope-migration.js`; additional one-off scripts are in `backend/src/scripts/`. Backend tests live in `backend/tests/`; client tests are under `client/tests/`. The audit inspected the source inventory, core routes/models/services, permission and scope helpers, navigation and representative frontend call sites, migrations and test coverage. It did not execute a production workflow.

**Status meanings:** F = fully implemented and verified at the repository/API-test level with a frontend call path traced in source; U = implemented but not verified end to end (usually no automated test or unavailable external provider); P = partially implemented; B = broken with reproducible evidence; M = missing; N/A = expressly outside approved scope. F is not a claim that a real operator completed browser acceptance or that Meta, SMTP, Razorpay, GST or other external services succeeded in production. A static UI or model alone never earns F.

**Completion rule:** Each of the 28 requested modules has two explicitly listed capabilities below, equally weighted. The numerator counts F only; U, P, B and M count zero until verified. N/A would be excluded, but none is excluded because no approved exclusions were provided. **19 F / 56 in-scope capabilities = 33.9% verification-backed completion.** This is an evidence score, not a measure of code volume or overall business readiness. All module scores are either 0%, 50%, or 100%; finer numbers would imply precision unsupported by the evidence.

**Competitor references:** E = eFlexo's [official features page](https://www.eflexo.in/features/) (job cards, multi-job invoices, delivery challans, reports, access control, WhatsApp/email/SMS, invoices, purchase, payment/salary, dashboard). F = FERObill's [official printing page](https://ferobill.com/erp-software-for-printing-industry/) (job cards, workflows, inventory/wastage, finance, CRM/HR/payroll, WhatsApp). D = FERObill's [digital-printing case study](https://ferobill.com/digital-printing/) (slab pricing, design uploads, approvals, stock and task allocation); this describes a client-specific solution, so it is **not** proof every FERObill installation contains those features. O = FERObill's [offset case study](https://ferobill.com/offset-printing/) (prepress, automated estimates, press/postpress and portal). These are verified **vendor-published claims**, not independently tested competitor functionality. Search for the exact name **Printpaza** did not establish an official product identity or reliable capability list; no feature or priority below is attributed to it.

**Effort:** engineering person-weeks (PW), including focused automated tests and basic UI integration, excluding discovery with a print shop, migration rehearsal, third-party onboarding, and release approval. P0 = financial/data-integrity or core operational blocker; P1 = competitive core; P2 = substantial enhancement; P3 = optional. Priorities are provisional until product scope is approved.

## Separate gap lists

**Missing features:** lead pipeline; sales orders; customer proof decision; workflow templates; machine/department work centres; job reservation; production material issue and waste; subcontract work orders; full-job QC/rework; multi-job challan and invoice; double-entry GL; automatic actual job costing; SMS transport; portal ordering/reordering/payment; branch master and branch stock/ledger; production KPIs; general migration/import; machine capacity/maintenance; repeat orders; job QR scanning; web-to-print (rows 1–28 above give implementation details).

**Partially implemented:** shared pricing (`CustomerPricing`/discount API versus local estimator defaults); print job specifications; fixed stage flow versus configurable routing; raw-material inventory versus production reservations; vendor/cost primitives versus subcontracting; activity logs versus immutable complete coverage. The proof workflow is substantial but customer approval is missing. Purchase and sales document primitives exist but consolidation is missing.

**Broken or demonstrably inconsistent:** `client/tests/vite-config.test.mjs:37-52` asserts that `https://api.carbonprintflow.com/api` must be refused as loopback even though `client/vite.config.ts:10-31` properly accepts it; a later test in the same file expects that hosted URL to load. This makes the client test suite fail for a test-data error, not a proved runtime build failure. `backend/src/models/Customer.js:126-132` sets `totalRevenue` from `Job.estimatedCost`, not invoiced revenue; the field name can mislead CRM decisions. This is a code-level defect requiring a focused regression test. No other production breakage is claimed without execution evidence.

**Technology and assurance gaps:** no automated browser E2E suite; estimator calculations have no identified tests; external SMTP/Meta/Razorpay operational paths were not exercised; no documented shared schema migration framework beyond the data-scope migration and scripts; standalone MongoDB uses compensating undo (`backend/src/utils/transactions.js`) and logs failures to undo, which merits fault-injection and reconciliation alerts for money/stock operations; module/action scopes and legacy fallbacks require a full endpoint-to-role matrix; audited print operations need immutable event IDs. Client's 10 node tests yielded 9 pass/1 fail as above. Backend API suite outcome is recorded in the verification section below.

**Competitive enhancements:** eFlexo's documented multi-job invoicing and challans are direct parity gaps. FERObill's public printing page positions workflow, inventory/wastage, and CRM/HR/payroll together; this application has most primitives but lacks the production-linked stock and costing loop. FERObill's case studies suggest slab pricing and customer proof collaboration as useful differentiators, but should be validated in a product demo before treating them as parity obligations. Machine scheduling, QR shop-floor tracking and web-to-print are product strategy opportunities rather than verified gaps against either named competitor.
